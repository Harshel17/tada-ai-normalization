Employee

GET

Retrieves the core Employee record, which contains the bulk of the information about an employee. Additionally, the response contains links to other operations to retrieve related data such as Pay Information or Demographics. The Employee operations use a separate security profile item to control access rights, located in the company security profile at: 1. `Modules -> REST API Resources -> Employees -> View`. 2. `Modules -> REST API Resources -> Employees -> ESS View`. 3. `Modules -> REST API Resources -> Employees -> Custom View`. <b>Only the 'REST API RESOURCES' security profile items, in combination with 'manager permissions', are considered by this REST API resource.</b> For ESS requests, the following fields are ignored: 'external_id', 'nickname', 'force_change_password', 'locked', 'status', 'add_to_new_hire_export', 'terminated', 'retired', 'deceased', 'in_touch'. The fields 'bsn', 'social_insurance', 'social_security', and 'national_insurance' are for backward compatibility and are populated if data exists. The new pattern for national identification numbers is represented by the 'national_id_numbers' field. For profiles where custom view is enabled, View permission can be customized for individual fields at: `HR -> Account/Personal Information (Employee Access) -> View/Edit(Custom) -> Permissions`. The state and state_code fields usually contain the same value. However, in some cases, state does not match the official state code. When an accurate or official state code is required, always use state_code

PUT

Updates the core employee information. The Employee operations use a separate security profile item to control access rights, located in the company security profile at: 1. `Modules -> REST API Resources -> Employees -> Edit`. 2. `Modules -> REST API Resources -> Employees -> ESS Edit`. <b>Only the 'REST API RESOURCES' security profile items, in combination with 'manager permissions', are considered by this REST API resource.</b> For ESS requests, the following fields are ignored if included in the PUT body: 'external_id', 'nickname', 'force_change_password', 'locked', 'add_to_new_hire_export', 'terminated', 'retired', 'deceased', 'in_touch'. <br/> For all other PUT requests, the following fields are ignored if included: 'id', 'terminated', 'links', 'EIN', 'external_id'. The fields 'bsn', 'social_insurance', 'social_security', and 'national_insurance' are for backward compatibility; the system uses old processing rules if they are included in the request. The new pattern for national identification numbers is represented by the 'national_id_numbers' field. <b>Note</b>: 'national_id_numbers' is ignored if the request contains any of 'bsn', 'social_insurance', 'social_security', or 'national_insurance'. For profiles where Custom view is enabled, Edit permission is disabled by default. If `effective_from` needs to be updated for a Cost Center, the ROOT `effective_from` must also be specified, like this: ```json "values": [ { "type": "ROOT", "effective_from": "1900-12-31" }, { "id": 10, "effective_from": "2013-11-23", "type": "ROOT" } ] ``` __If you want to apply the default settings of the cost center.__ You should set the `apply_defaults` field to `true` in the request body like this: ```json "cost_center_info": { "defaults": [ { "index": 2, "value": { "id": 50 }, "apply_defaults": true } ] } ``` __Termination:__ `status` field value must be set to the one of existing account statuses with a type equal to "Terminated". `termination_details` field is required. The schema of this API will vary depending on the configuration of the company e.g. enabled sub-systems, manager configuration etc. Certain fields listed on the schema may not be required if they are not configured in the termination process of the company. HR: `termination_reason`, `termination_notes`, `managers_at_termination`, `rehireable`, `notice`, `benefits_end_date`, `benefit_coverage_end_date` HR & Payroll: `deduction_end_date`, `direct_deposit_end_date`, `earning_end_date` The fields `termination_reason`, `termination_notes`, `managers_at_termination` may also be required depending on the configuration defined in Company Settings. To terminate an employee, it may be required to resolve issues with existing configuration/data that exists past the employee's termination date. For example pending timeoff requests can either be approved or rejected. Refer to the schema for the correct 'solution' for each of the following: `manager_groups_solutions` - required if employee is a 'Manager 1-6' for the employee(s). `other_groups_solution` - required if employee has access to other group(s). `pto_requests_after_termination_solution` - required if employee has some hours of Pending Time Off Request which fall past termination date. `pto_requests_before_termination_solution` - required if employee has some hours of Pending Time Off Request which fall before termination date. `time_entries_after_termination_solution` - required if employee has Time Entries which fall past termination date. `accrual_not_up_to_date_solutions` - required if accruals for {time_off_name} are Not Accrued up to terminated date. `accrual_over_calculated_solutions` - required if accruals for {time_off_name} are Accrued past terminated date. `security_profile_solution` - required if employee was the only account assigned to {security_profile_name} security profile. `assignments_solution` - required if employee has vehicle(s)/asset(s) assigned. `badges_solution` - required if employee has active badge/s with effective date/s fall past termination date. `account_benefit_plan_solution` - required if employee has future benefit plan(s). `accrual_pay_out_solution` - required if employee can not be paid out. `scheduled_performance_review_solution` - required if scheduled performance review pending. Available options are `delete`, `initiate`, `ignore` and `skip`. `in_progress_performance_review_solution` - required if in progress performance review pending. Available options are `delete`, `end` and `ignore`. `performance_review_to_do_solution` - required if employee has performance review todos. `my_to_do_solution` - required if employee has open my to do items. __Rehiring:__ `status` field value must be set to the one of existing account statuses with a type NOT equal to "Terminated". `rehire_details` field is required. `rehire_details` includes `rehire_as_of_date` field only. __Transition from active status to another active:__ There is ability to change account status from one active status to another active. Only `status` field needs to be specified.

PATCH

Applies partial updates to an employee resource using JSON Patch. The Employee operations use a separate security profile item to control access rights, located in the company security profile at: 1. `Modules -> REST API Resources -> Employees -> Edit`. 2. `Modules -> REST API Resources -> Employees -> ESS Edit`. <b>Only the 'REST API RESOURCES' security profile items, in combination with 'manager permissions', are considered by this REST API resource.</b> The PATCH request works by retrieving the <b>current employee state</b> using a GET request. It then applies the operations provided in the PATCH request <b>on top of the current employee state</b>, and then sends the updated data via a PUT request. Refer to the Employee V2 GET and PUT requests to determine which fields can be modified. <b>Ignored Fields in PATCH Requests</b> <b>- For ESS Requests:</b> The following fields will be ignored: - `external_ID` - `nickname` - `force_change_password` - `locked` - `status` - `add_to_new_hire_export` - `terminated` - `retired` - `deceased` - `in_touch` <b>- For Other PATCH Requests:</b> The following fields will be ignored: - `id` - `status` - `terminated` - `links` - `EIN` - `external_ID` Additionally, the national_id_numbers field will be ignored if the <b>current employee state</b> contains any of the following fields: - `bsn` - `social_insurance` - `social_security` - `national_insurance` <b>Backward Compatible Fields</b> The following fields are left for backward compatibility and the system will use old process rules if they are added to the request: - `bsn` - `social_insurance` - `social_security` - `national_insurance` <b>Note</b>: 'national_id_numbers' will be ignored if request contains any of 'bsn', 'social_insurance', 'social_security' and 'national_insurance' fields. For profiles where Custom view is enabled, Edit permission is disabled by default. <b>Example Request:</b> To replace/add/remove attributes in the request body, consider the following example: **Existing Employee Data:** ```json { "nickname": "nickname", "salutation": "Mr", "address": { "country": "IND" }, "account_extra_fields": [ { "index": 3, "values": [ { "value": "East" } ] }, { "index": 4, "values": [ { "value": "Employee" } ] } ] } ``` **PATCH Request Body:** ```json [ { "op": "replace", "path": "/nickname", "value": "NewNickname" }, { "op": "add", "path": "/primary_email", "value": "abc@ukg.com" }, { "op": "replace", "path": "/address/country", "value": "USA" }, { "op": "remove", "path": "/salutation" }, { "op": "add", "path": "/managers", "value": [] }, { "op": "add", "path": "/managers/0", "value": { "index": 0, "empl_ref": {} } }, { "op": "add", "path": "/managers/0/empl_ref/account_id", "value": 4341264964 }, { "op": "replace", "path": "/managers/0/empl_ref/account_id", "value": 4341264962 }, { "op": "add", "path": "/account_extra_fields/-", "value": {"index": 0, "values":[ {"value": "Safty" } ] } }, { "op": "replace", "path": "/account_extra_fields/0/values/0/value", "value": "East" }, { "op": "remove", "path": "/account_extra_fields/1" } ] ``` **Updated Employee Data:** ```json { "nickname": "NewNickname", "primary_email": "abc@ukg.com", "address": { "country": "USA" }, "managers": [ { "index": 0, "empl_ref": { "account_id": 4341264962 } } ], "account_extra_fields": [ { "index": 0, "values": [ { "value": "Safty" } ] }, { "index": 3, "values": [ { "value": "West" } ] } ] } ```

DELETE

The ability to delete an employee also depends on the Pay Statement status. If the Pay Statement is 'Open', 'Closed', or 'Finalized', deletion is restricted.
