# Authentication
Currently two oAuth flows are supported for authentication, both require the configuration of an oAuth Application within the system prior to their use.

## OAuth Application

An OAuth Application is an industry standard protocol to allow a website or application to access resources hosted by other web apps on behalf of a user.  Here are some key points about OAuth 2.0:
- Authorization: OAuth 2.0 is primarily an authorization protocol, not an authentication protocol. It grants access to resources (e.g., APIs or user data) without sharing user credentials.
- Access Tokens: OAuth 2.0 uses Access Tokens to represent authorization. These tokens allow client apps to access resources on behalf of the user.
- Roles:
    - Resource Owner: The user who owns protected resources and grants access.
    - Client: The system requiring access to resources (must hold an Access Token).
    - Authorization Server: Issues Access Tokens upon successful authentication and consent.
    - Resource Server: Protects user resources and validates Access Tokens.
    - Authorization Code Flow: Instead of directly returning an Access Token, the authorization server may return an Authorization Code, which is then exchanged for an Access Token.


OAuth enables secure delegated access, decoupling authentication from authorization.

To create an OAuth Application within the system, navigate to the Company Setup screen by following this path `Settings > Global Setup > Company Setup`. Locate the widget titled `OAuth Applications`, so that a new OAuth Application can be created and linked with the system.

## Client Credentials

The Client Credentials Flow (defined in <a href="https://tools.ietf.org/html/rfc6749#section-4.4" target="_blank"> OAuth 2.0 RFC 6749, section 4.4 <i class="fa fa-external-link" aria-hidden="true"></i></a>) involves an application exchanging its application credentials, such as client ID and client secret, for an access token.

This flow is best suited for Machine-to-Machine (M2M) applications, such as CLIs, daemons, or backend services, because the system must authenticate and authorize the application instead of a user.

This flow should be used for accessing the REST API in machine-to-machine communication for external integrations. An access_token is returned by the <a href="/ta/docs/rest/public/?r=__v2__companies__(cid)__oauth2__token">Token</a> endpoint when requested with valid client_id and client_secret.

The client_id and client_secret are defined by an OAuth Application within the system with type 'Machine to Machine'.

# Authorization
Requests to the REST API are authorized by checking if security profile of the authenticated account (Auth Code Flow) or Client Credential (Client Credential Flow) contains the security item required for access to the endpoint.

Security profiles when used with the REST APIs work in exactly the same way as with interactive logins (via the user interface).
